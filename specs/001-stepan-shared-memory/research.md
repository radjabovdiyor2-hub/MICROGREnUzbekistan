# Phase 0 — Research: Единая память Стёпана

Все неизвестные из Technical Context разрешены. Ниже — принятые решения с обоснованием и отвергнутыми вариантами.

---

## D1. Где хранить разговор

**Решение**: таблица в PostgreSQL, объявленная в `packages/database/prisma/schema.prisma`.

**Обоснование**: конституция называет `schema.prisma` единым источником DDL и запрещает ручной SQL DDL. База уже общая для витрины и ИИ-офиса, отдельного хранилища заводить не нужно. Разговор — это записи, к которым нужен упорядоченный доступ по времени и фильтр по владельцу; реляционная таблица покрывает это индексом.

**Отвергнуто**:
- *Redis* — переживает перезапуск бота, но не перезапуск Redis, и не даёт истории за 30 дней (SC-004). Redis в проекте занят Event Bus и кэшем.
- *Расширение модели `AiChat`* — она про переписку покупателя с консультантом витрины, ключ `userId` ссылается на `User` (покупателя). Смешивать разговор владельца с клиентскими нельзя: FR-010 и SC-006 требуют разделения.
- *Файловая очередь как у Bot Bus* — не даёт запросов по времени и фильтров, а объём здесь другой.

## D2. Как Telegram-сторона попадает в память

**Решение**: `apps/tgas` ходит по HTTP в `apps/web`, заголовок `x-bot-secret`.

**Обоснование**: принцип I конституции — связь между модулями только через HTTP API или Event Bus. Оба конца механизма уже существуют:
- `apps/web/src/lib/adminAuth.ts` принимает `BOT_SECRET` для server-to-server (явно описано в шапке файла);
- `BOT_SECRET` уже прокинут ботам в `docker-compose.prod.yml` с комментарием «Must match the web service's BOT_SECRET so admin API calls authorize»;
- Стёпан уже так вызывает журнальные кроны (`stepan_bot/main.py:643, 656, 671`).

Новых способов связи не появляется, новых секретов тоже.

**Отвергнуто**:
- *Прямой SQL из `apps/tgas`* — короче на один хоп, но прямо нарушает принцип I. Прецеденты в репозитории есть (`UPDATE tasks`, `INSERT INTO storefront_outbox`), они зафиксированы как долг в `docs/AUDIT-2026-07.md`; наследовать долг в новом коде нельзя. Плюс пришлось бы дублировать логику доступа на двух языках и держать её синхронной при изменении схемы.
- *Через `web_office`* — `web_office` живёт в `apps/tgas`, а данные принадлежат Prisma-стороне. Получился бы лишний хоп tgas → tgas → web без выигрыша.

## D3. Базовый URL витрины для ботов

**Решение**: новая настройка в `apps/tgas/shared/config.py` со значением по умолчанию `http://web:3000`, прокидывается в compose.

**Обоснование**: боты и веб живут в одной сети `mg_net`, где веб доступен по имени сервиса `web` на порту 3000. Хост-порт `3002` наружу здесь не при чём.

**Прямо не копировать существующий образец**: журнальные кроны Стёпана стучатся на `http://127.0.0.1:{PORT}` с комментарием «We assume Next.js runs on 3000 or 3005, typical dev ports». Внутри контейнера `mg_stepan` по этому адресу ничего нет — веб в другом контейнере. Все три вызова (`prepare`, `finalize`, `print-run`) в продакшене отказывают, и `except` только пишет в лог. Это отдельный дефект, зафиксирован в `docs/AUDIT-2026-07.md`; новый код обязан использовать настройку, а не хардкод.

**Отвергнуто**:
- *Переиспользовать `settings.storefront_url`* — свойство помечено `[DEPRECATED]` и возвращает `database_url`, а не HTTP-адрес.

## D4. Чей это разговор — ключ владельца

**Решение**: на первом шаге — один общий разговор владельца. Ключ постоянный, к нему обращаются все сессии с ролью `ADMIN` в вебе и все идентификаторы из `admin_telegram_ids` в Telegram.

**Обоснование**: общего идентификатора личности между каналами сегодня не существует. Веб-сессия несёт `{ role, name?, fp }` — стабильного идентификатора администратора в ней нет (`apps/web/src/lib/session.ts`). Telegram опознаёт владельца по списку числовых ID. Чтобы дать каждому администратору свою нить, пришлось бы менять содержимое сессии и заводить связь «сессия ↔ сотрудник» — это отдельная работа по авторизации, к памяти отношения не имеющая.

Безопасность при этом не страдает: доступ к `/api/admin/*` требует роли `ADMIN` (`isAuthorized`), роль `SELLER` туда не проходит. FR-012 выполняется.

**Это пересматривает допущение спецификации** о раздельных разговорах на каждого администратора. Фактически сегодня владелец один, и разделение ничего не даёт. Путь миграции, когда администраторов станет несколько: добавить стабильный идентификатор в полезную нагрузку сессии, связать с `Employee.telegramId` (поле уже есть и уникально) и заменить постоянный ключ на этот идентификатор. Схема к этому готова — ключ владельца выделен отдельным полем, а не зашит в структуру.

**Отвергнуто**:
- *Ключ по каналу* — ровно та болезнь, которую лечим.
- *Ключ по `name` из сессии* — поле необязательное и не уникальное.

## D5. Сколько истории отдавать модели

**Решение**: хвост последних сообщений с двойным ограничением — по количеству и по суммарной длине; при превышении отбрасываются самые старые.

**Обоснование**: FR-009 требует предсказуемой стоимости обращения. Роут `/api/admin/stepan` уже ограничен по частоте (20 запросов в минуту) с комментарием «Каждый вызов стоит денег: цикл рассуждения — это несколько запросов к модели». Ограничение по количеству само по себе не спасает: одно сообщение может быть расшифровкой длинного голосового.

**Отвергнуто**:
- *Вся история целиком* — стоимость растёт неограниченно, качество ответа падает.
- *Суммаризация старых частей моделью* — дополнительный вызов модели на каждый запрос, то есть удорожание ради экономии. Кандидат на будущее, если хвоста перестанет хватать.

## D6. Порядок сообщений при одновременной работе в двух каналах

**Решение**: порядок задаёт момент записи на сервере, а не время устройства; выдача сортируется по нему и по идентификатору записи как разрешению ничьей.

**Обоснование**: клиентские часы расходятся, а владелец физически может писать с телефона и ноутбука одновременно. Идентификатор записи монотонен, поэтому пара «время, идентификатор» даёт устойчивый порядок.

## D7. Что делать, когда хранилище недоступно

**Решение**: ассистент отвечает, но явно предупреждает, что отвечает без памяти. Запрос не притворяется успешным.

**Обоснование**: FR-007. Это тот же класс дефекта, который год держал «Пульт ИИ» мёртвым и который аудит нашёл ещё в двух местах — журнал действий и регистрация возвращают успех при упавшей базе. Повторять его в новом коде нельзя. Образец правильного поведения уже есть в `apps/web/src/app/api/admin/bots/route.ts`: «если офис не отвечает — это САМО ПО СЕБЕ важная новость».

**Отвергнуто**:
- *Отказать в ответе целиком* — владелец теряет возможность работать из-за проблемы, которая его вопроса не касается.
- *Ответить молча без контекста* — владелец получит невпопад и не поймёт почему.

## D8. Что делать с историей в FSM aiogram

**Решение**: FSM перестаёт быть источником истории разговора и остаётся тем, чем должен быть — состоянием текущего шага диалога. Существующая функция запоминания обмена переключается на общее хранилище.

**Обоснование**: два источника истории означают расхождение. В `assistant.py` уже есть точка, через которую проходит каждый обмен, — именно её и переключаем, не размазывая запись по обработчикам.
