# Security Policy — Microgreen Uzbekistan

Обзор мер безопасности платформы (веб-магазин `apps/web` + AI-офис `apps/tgas`).
Документ для технического Due Diligence и внутренней эксплуатации.

## 1. Модель угроз (кратко)
| Актив | Угроза | Контрмера |
|---|---|---|
| Персональные данные клиентов (имя, телефон, Telegram ID) | Утечка/несанкц. доступ | Хранение только в локальной БД, доступ по сети `mg_net`, TLS в транзите |
| Платёжный money-state (оплата заказа) | Подделка колбэка, двойное списание | Проверка подписи Click (MD5) / авторизации Payme (Basic), атомарный идемпотентный переход в PAID |
| Межботовые события | Инъекция поддельных событий | `EVENT_BUS_SECRET` (заголовок `X-Bot-Secret`) на `/event` |
| Секреты (токены, ключи API) | Утечка в репозиторий/логи | `.env` вне git, секрет-скан gitleaks, ротация |
| Админ-действия (веб-офис, POS) | Несанкц. доступ | RBAC (роли), PIN для POS, INGEST_SECRET/BOT_SECRET между сервисами |
| Инфраструктура (БД, Redis) | Доступ из интернета | Порты 5432/6379/8050 привязаны к `127.0.0.1`, наружу только nginx/TLS |

## 2. Управление секретами
- Все секреты (токены ботов, ключи OpenAI/Gemini, токены Instagram/Facebook, пароли БД,
  ключи платёжных систем) хранятся в `.env` на сервере. `.env` **не отслеживается git**.
- Секрет-скан: `.gitleaks.toml` в корне — прогонять `gitleaks detect` перед пушем / в CI.
- ⚠️ **Историческая утечка:** репозиторий ранее был публичным, и в git-историю попадали
  рабочие токены (см. incident 07.2026). HEAD очищен, но **история компрометирует
  попавшие туда ключи навсегда**. Обязательные ручные действия (ops):
  1. Revoke токена бота в BotFather + выпуск нового; обновить `.env` на сервере, рестарт.
  2. Ротация Instagram/Facebook токенов и паролей Postgres.
  3. Репозиторий сделать приватным; при необходимости — purge истории (git filter-repo / BFG).
  4. На сервере: смена пароля `ubuntu`, переход на SSH-ключи, ревизия `authorized_keys`.

## 3. Сеть и инфраструктура
- **nginx** reverse-proxy c TLS/SSL — единственная точка входа снаружи.
- Контейнеры изолированы в docker-сети `mg_net`; межсервисный трафик не выходит наружу.
- **Postgres (5432), Redis (6379), web_office (8050)** привязаны к `127.0.0.1` — недоступны
  из интернета напрямую. Боты обращаются к БД/Redis по внутренним именам сети, не через хост-порты.
- Event-bus порты `808x` **не публикуются** на хост (только внутри `mg_net`).
- Логи: docker `json-file` с ротацией (`max-size: 10m`, `max-file: 5`).

## 4. Аутентификация и авторизация
- **Единый шлюз:** роль проверяется в `apps/web/src/middleware.ts` до вызова обработчика.
  Новый маршрут под защищённым префиксом (`/api/admin/*`, `/api/inventory/*`, запись в
  `/api/products`, `/api/upload`, `/api/notify`) закрыт по умолчанию.
- **Сессия:** подписанный HS256-токен (`jose`) в httpOnly-cookie `mg_session`, срок 12 ч.
  JS её не читает — XSS не может её угнать. Смена `SESSION_SECRET` разлогинивает всех
  (аварийный рубильник).
- **Пароль владельца:** scrypt с солью (`lib/password.ts`). Источники по приоритету:
  `.admin-password.json` → `ADMIN_PASSWORD_HASH` → `ADMIN_PASSWORD`. Ни один не задан —
  в проде вход закрыт (fail closed). Лимит 10 попыток / 15 мин на IP.
- **POS-терминал / сотрудники:** 4-значный PIN (`Employee.pin`, уникальный),
  лимит 5 попыток / 15 мин на IP, успешный вход выдаёт сессию с ролью `SELLER`.
- **Сервис→веб (admin API):** заголовок `x-bot-secret` (`BOT_SECRET`).
- **Внешний ingest в веб-офис:** заголовок `X-Ingest-Secret` (`INGEST_SECRET`); при отсутствии
  ключа в проде запрос отклоняется (money-state никогда не меняется по неаутентиф. запросу).
- **Событие бот→бот:** заголовок `X-Bot-Secret` (`EVENT_BUS_SECRET`) на `/event`.
- **Журнал действий:** `lib/audit.ts` пишет JSON Lines в `logs/audit-<дата>.jsonl` и в stdout
  (попадает в docker-логи). Фиксируются входы, отказы, смена пароля, обращения к
  персональным данным.

> Роли в схеме (`enum Role { USER ADMIN MODERATOR SELLER }`) существовали и раньше, но
> **ни один маршрут их не проверял** — доступ держался на пароле в `sessionStorage`.
> Описание выше отражает состояние после исправления.

## 5. Платёжная безопасность (Click / Payme)
- Заказ переходит в `PAID` **только** после успешной проверки подписи/авторизации провайдера
  с настроенными ключами. При отсутствии ключей маршрут **не** трогает money-state.
- **Click:** проверка MD5-подписи (`sign_string`) + сверка суммы; `action=1` (Complete) —
  подтверждение оплаты.
- **Payme:** HTTP Basic `Paycom:<PAYME_KEY>`; методы JSON-RPC (Check/Create/Perform/Cancel).
- **Идемпотентность:** переход `PENDING→PAID` — атомарный условный `updateMany`; побочные
  эффекты (уведомление клиента, синхронизация в CRM, запись дохода) срабатывают ровно один раз
  даже при повторной доставке колбэка.
- Follow-up: полноценная сертификация Payme требует таблицы транзакций для сверки
  Create/Perform/Cancel по transaction id (в планах).

## 5а. Ограничение частоты запросов
`lib/rateLimit.ts` — счётчик в памяти процесса (`web` работает одним контейнером).

| Маршрут | Лимит | Зачем |
|---|---|---|
| `/api/auth/password` | 10 / 15 мин | перебор пароля |
| `/api/inventory/employees/auth` | 5 / 15 мин | PIN — всего 10 000 комбинаций |
| `/api/ai/chat` | 20 / мин | защита бюджета Gemini (включая vision) |
| `/api/reviews` | 10 / час | спам отзывами |
| `/api/users/data` | 5 / час | тяжёлая выгрузка, необратимое удаление |

Дополнительно nginx режет `/api/` на 10 r/s с burst 20.

## 6. Безопасность данных
- Транзит: HTTPS/TLS для всех внешних соединений.
- Хранение: персональные данные — только во внутренней БД; третьим лицам не передаются.
- Параметризованные запросы (Prisma / SQLAlchemy `text()` с bind-параметрами) — защита от SQL-инъекций.
- Соответствие Закону РУз «О персональных данных»: данные пользователей на локальных серверах.

## 6а. Права субъекта персональных данных
Маршрут `POST /api/users/data` (личность подтверждается подписанным Telegram `initData`):
- `action: export` — выгрузка профиля, заказов, отзывов и адресов одним JSON;
- `action: delete` — удаление отзывов и адресов, обезличивание профиля (`telegramId`,
  телефон, имя, аватар затираются).

Заказы при удалении сохраняются обезличенными: они первичный учётный документ, их хранение
требует налоговое законодательство. Реализует ст. 20 Закона РУз «О персональных данных».

## 6б. Принятые риски
Осознанно оставленные ограничения — чтобы они не всплыли как «скрытая находка» при аудите.

| Риск | Почему принят | Условие снятия |
|---|---|---|
| `sharp` 0.34.x в составе `next` (CVE-2026-33327/33328/35590/35591, libvips) | `next@16.2.12` держит его как `optionalDependency "^0.34.5"`; исправление вышло в 0.35, npm-override вложенный экземпляр не перебивает. Загрузка файлов закрыта ролью ADMIN, внешние источники картинок ограничены `remotePatterns` | обновление `next` на `sharp ^0.35` |
| `postcss` ≤8.5.17 в составе `next` (GHSA-r28c-9q8g-f849 — path traversal при авто-загрузке source map; GHSA-qx2v-qp2m-jg93 — XSS через неэкранированный `</style>`) | Найден проверкой 31.07.2026. `next@16.2.12` тянет собственный вложенный экземпляр, npm-override его не перебивает; `npm audit fix --force` откатывает `next` до 14.2.35, то есть ломающее изменение. Эксплуатация требует контроля над CSS-исходником, а он у нас свой — пользовательский CSS никуда не принимается | обновление `next` на `postcss ≥8.5.18` |
| Вход по Face ID (WebAuthn) отключён | Прежняя реализация **не проверяла подпись**: `login-verify` сверял только id учётки, который `login-options` сам и отдавал — вход владельцем выполнялся двумя HTTP-запросами. Мёртвый код удалён, login возвращает 501 | переписать на `@simplewebauthn/server` + перерегистрация ключей |

### Снятые риски (июль 2026)
- **CSP `unsafe-inline`/`unsafe-eval`** → заменён на nonce-based CSP (`middleware.ts`).
- **Счётчик лимитов в памяти** → `rateLimit.ts` поддерживает Redis через `REDIS_URL`, fallback на in-memory.
- **Payme без таблицы транзакций** → модель `PaymeTransaction` + полный CRUD в `/api/payment/payme`.
- **Order sync fire-and-forget** → retry с exponential backoff (3 попытки).
- **docker.sock у devops** → mount убран.
- **Хардкод IP сервера в скриптах** → вынесен в `DEPLOY_HOST`/`DEPLOY_USER` env vars.

## 7. Реагирование на инциденты
1. Обнаружение (алерты heartbeat/ошибок ботов у Стёпана, аномалии в логах).
2. Локализация (изоляция сервиса, revoke затронутых секретов).
3. Ротация ключей, рестарт, проверка `authorized_keys`/`last` на сервере.
4. Post-mortem и обновление этого документа.
