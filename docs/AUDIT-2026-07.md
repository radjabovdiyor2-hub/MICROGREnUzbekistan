### Живой прогон пульта

На стенд подняли `web_office` с текущим исходником и отправили все 15 действий плюс контрольное несуществующее.

| Результат | Действий |
|---|---|
| HTTP 200, `status: "pending"` | 15 из 15 |
| HTTP 400, «действие не разрешено» | только контрольное `__bogus_action__` |

`pending` здесь — правильный ответ: задача поставлена в очередь, ботов на стенде не запускали, поэтому подтверждения исполнения нет. Проверили саму очередь — все 15 задач легли в `bus_tasks/pending` с верной адресацией. Например, `daily_kpi_snapshot` ушёл `to_bot: analytics_bot`, хотя UI прислал подсказку `bot: web_office` — то есть белый список действительно переопределяет UI, как и задумано.

Отдельно подтверждено: `sync_catalog_from_storefront` теперь отвечает 200/`pending` вместо прежнего 400. Дефект закрыт не только в коде, но и в поведении.

Тестовые задачи из очереди после прогона удалены — среди них `send_broadcast` и `b2b_outreach`, которые при запуске ботов ушли бы реальным клиентам.

## 2. Правильность логики

Систематически искали класс дефекта, который год держал пульт мёртвым: **отказ, отданный наружу как успех**. Просмотрено 88 route-файлов витрины. Найдено два живых случая.

### P1 — журнал аудита врёт при отказе БД

[apps/web/src/app/api/admin/audit/route.ts:61](../apps/web/src/app/api/admin/audit/route.ts#L61)

```ts
} catch (error) {
  console.error('[audit] чтение журнала не удалось:', error);
  return NextResponse.json({ status: 'ok', entries: [], nextCursor: null });
}
```

Владелец видит пустой журнал и заключает «действий не было», хотя на деле база недоступна. Для журнала аудита это худший из возможных отказов: он маскирует именно ту ситуацию, ради которой журнал и ведётся.

**Как надо:** отдавать 503 и явную ошибку, как это уже делает [api/admin/bots/route.ts:18](../apps/web/src/app/api/admin/bots/route.ts#L18) («если офис не отвечает — это САМО ПО СЕБЕ важная новость»).

### P1 — регистрация возвращает успех при упавшей БД

[apps/web/src/app/api/auth/register/route.ts:52](../apps/web/src/app/api/auth/register/route.ts#L52)

```ts
} catch (error) {
  console.error('Register error:', error);
  // Even if DB fails, return success for local-only auth
  return NextResponse.json({ success: true, user: null });
}
```

Клиент видит «вы зарегистрированы», аккаунта нет. Дальше он не сможет войти и не поймёт почему. Комментарий объясняет намерение (локальная авторизация), но цена ошибки — молча потерянные регистрации.

**Как надо:** различать «БД недоступна» (503, честное сообщение) и сценарий local-only, если он вообще нужен.

### Наблюдение по архитектуре, не дефект

Бекап по расписанию делает Стёпан напрямую ([stepan_bot/main.py:525](../apps/tgas/bots/stepan_bot/main.py#L525) → `shared.backup.daily_backup_task`), а не диспетчеризует в `devops_bot`, у которого для этого есть свой обработчик шины. Общая логика одна, точек входа две. Работает, но модель «DevOps владеет бекапами» не соответствует коду.

## 3. Веб и боты как одно целое

**Стык данных — да. Стык разума — нет.**

### Что действительно связано

- **Пульт ИИ.** `AdminBotControl.tsx` → `/api/admin/bot-action` → `web_office:8050` → белый список → Bot Bus → бот. Контракт `{status: ok|pending|error}`, `pending` — честное «в очереди», а не провал.
- **Ingest витрина → офис**, все шесть потоков: заказ ([api/orders/route.ts:135](../apps/web/src/app/api/orders/route.ts#L135)), статус заказа ([lib/orderSync.ts](../apps/web/src/lib/orderSync.ts)), клиент (регистрация + telegram-webapp), поддержка, B2B-лид, отзыв — через [lib/office.ts](../apps/web/src/lib/office.ts).
- **Здоровье ботов** выведено в админку: `/api/admin/bots` и `/api/admin/bot-jobs` ходят в офис через общий клиент [officeFetch](../apps/web/src/lib/office/client.ts).

Два клиента офиса в витрине — это не дублирование, а разная семантика: `lib/office.ts` — исходящие сигналы «выстрелил и забыл» (таймаут 4 с, ошибки глотаются намеренно), `lib/office/client.ts` — запрос-ответ админки (15 с, честная ошибка). Настоящее дублирование только в двух местах: [bot-action/route.ts:53](../apps/web/src/app/api/admin/bot-action/route.ts#L53) и [departments/route.ts:21](../apps/web/src/app/api/admin/departments/route.ts#L21) ходят в офис сырым `fetch` мимо `officeFetch` (P2).

### P1 — Стёпан это два разных ИИ

Комментарий в [api/admin/stepan/route.ts](../apps/web/src/app/api/admin/stepan/route.ts) утверждает: «Тот же Стёпан, что и в Telegram: одна база, одна шина». База и шина — да. Разум — нет.

| | Telegram | Админка |
|---|---|---|
| Реализация | [assistant.py](../apps/tgas/bots/stepan_bot/handlers/assistant.py), 1930 строк Python | [lib/stepan/brain.ts](../apps/web/src/lib/stepan/brain.ts) + [tools.ts](../apps/web/src/lib/stepan/tools.ts), 751 строка TS |

Практический смысл: «Стёпан, подними цену на микс» работает в админке и не работает в Telegram. «Стёпан, перекличка» — наоборот. Владелец не может знать, что где доступно.

Третий реестр возможностей — [shared/capabilities.py](../apps/tgas/shared/capabilities.py), 10 действий отделов — используется путём исполнения планов и не пересекается ни с одним из двух наборов.

### P1 — у веб-Стёпана нет памяти

[AdminStepan.tsx:49](../apps/web/src/components/admin/AdminStepan.tsx#L49) держит переписку в `useState`. Ни localStorage, ни базы. Роут [stepan/route.ts:43](../apps/web/src/app/api/admin/stepan/route.ts#L43) принимает историю из тела запроса и нигде её не сохраняет.

Следствия: перезагрузил вкладку — контекст стёрт; начал в Telegram — в админке не видно; в Telegram история живёт в FSM-состоянии aiogram и умирает вместе с ним. Модель `AiChat` в схеме относится к клиентскому виджету витрины (ключ — `userId` покупателя), для разговоров владельца хранилища нет.

## 4. Насколько это «Джарвис»

Точной копии не будет: у Джарвиса AGI, голограммы и управление физическими объектами. Но по функциям управления бизнесом основа уже построена — не хватает трёх вещей.

### Что уже есть

| Способность Джарвиса | Состояние |
|---|---|
| Понимает задачу словами, а не кнопками | Есть: NL-диспетчер `brain` в обоих каналах |
| Слышит голос | Есть в Telegram ([assistant.py:808](../apps/tgas/bots/stepan_bot/handlers/assistant.py#L808) → `ai.transcribe_audio`). В админке — нет |
| Делает реальные дела, а не отчитывается | Есть: [capabilities.py](../apps/tgas/shared/capabilities.py) требует доказательств — кому, сколько, куда |
| Спрашивает разрешения на важное | Есть: `/api/admin/stepan/execute` отделён от рассуждения |
| Следит сам, без напоминаний | Есть: 12 расписаний — дедлайны, follow-up, вечерняя сводка, недельный отчёт, здоровье ботов каждые 5 минут, KPI-watchdog, бекап в 03:00 |
| Командует подчинёнными | Есть: Event Bus + Bot Bus, 13 отделов, перекличка |
| Помнит разговор поверх каналов | **Нет** (см. §3) |
| Отвечает голосом | Есть в Telegram: на голосовой вопрос Стёпан отвечает голосом ([assistant.py:1199](../apps/tgas/bots/stepan_bot/handlers/assistant.py#L1199) → `ai.generate_speech`). В админке — нет |
| Сам выходит на связь при проблеме | **Частично**: сигналы формируются, но доходят в Telegram, не в админку |

### Три разрыва до цели

1. **Голос есть только в Telegram.** Синтез речи в [ai_engine.py:688](../apps/tgas/shared/ai_engine.py#L688) работает, и Стёпан озвучивает ответ, если вопрос был голосовым. Не хватает микрофона в админке поверх существующего `think()`. Реализаций синтеза при этом две: OpenAI `tts-1` в `ai_engine` и бесплатный `edge_tts` в [apps/bot/services/tts_service.py](../apps/bot/services/tts_service.py) — витринный бот и офис озвучивают разными голосами через разных поставщиков.
2. **Память привязана к каналу.** Нужна модель разговора владельца с ключом по владельцу, а не по каналу; оба мозга пишут и читают её.
3. **Проактивность не доходит до веба.** Расписания есть, канал доставки «офис → админка» отсутствует; [AdminNotifications.tsx](../apps/web/src/components/admin/AdminNotifications.tsx) ждёт источник. Правило: сообщать не факт, а факт плюс готовое решение одной кнопкой в тот же confirm-flow.
