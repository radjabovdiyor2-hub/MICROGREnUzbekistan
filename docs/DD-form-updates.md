## §4. Arxitektura va texnologiyalar

**№3 Front-end — TypeScript strict mode** 🔴
Заявлено «strict mode — kompilyatsiya vaqtida xatolarni aniqlash», но в
`next.config.ts` стоял `typescript.ignoreBuildErrors: true` — ошибки типов
не блокировали прод-сборку. Флаг снят, `tsc --noEmit` проходит с 0 ошибок.
Формулировка теперь соответствует коду.

**№7 Keshlash (Redis) — rate limiting** 🔴
Заявлено «Redis 7 — API so'rovlarni cheklash (rate-limiting)». Ограничения
частоты не существовало ни в каком виде. Реализовано в `lib/rateLimit.ts`
(счётчик в памяти процесса, `web` работает одним контейнером).
**Новый текст:** «Redis 7 (Alpine) — vaqtinchalik keshlar va Pub/Sub.
Rate-limiting: nginx (10 r/s, burst 20) + пер-маршрутные лимиты в приложении
(вход 10/15 мин, PIN 5/15 мин, AI-чат 20/мин, отзывы 10/час)».

**№8 Monitoring** 🟡
Было: «Eslatma: ELK/Grafana/Prometheus hali ulangan emas».
**Новый текст:** «Prometheus + Grafana (`docker-compose.monitoring.yml`),
node-exporter и cAdvisor. Приложение отдаёт `/api/metrics` (счётчики входов,
отказов, бизнес-показатели) и `/api/health?ready=1` (liveness + проверка БД).
14 правил алертинга: доступность, диск, память, всплеск неудачных входов.
Все порты — только на 127.0.0.1, доступ через SSH-туннель».

**№10 CI/CD** 🟡
Было: «CI/CD pipeline (GitHub Actions) hali sozlanmagan» — на деле пайплайн

## §5. AI — инфраструктура модели

**№15 Xavfsizlik — «Foydalanuvchi kiritmalari sanitizatsiya qilinadi»** 🔴
Пользовательский ввод не санитизировался. Текст отзыва и имя гостя
попадали в `<script type="application/ld+json">` на странице товара через
`JSON.stringify`, который не экранирует `<` — то есть отзыв вида
`</script><script>…` выполнялся у каждого посетителя. Отзывы принимались без
авторизации, CSP содержит `'unsafe-inline'`.
Исправлено: экранирование в `lib/seo/jsonLd.ts`, ограничение длины,
лимит частоты. Формулировку можно оставить — теперь она верна.

**№15 «Maxsus adversarial testing o'tkazilmagan»** 🟢 — по-прежнему честно.

## §6. Xavfsizlik

**№2 Secure Coding — dependency** 🟡
Было 12 уязвимостей высокого уровня. `next` поднят 16.1.6 → 16.2.12,
`sharp` закреплён на ^0.35.3. Осталось 3 (вложенный `sharp` внутри `next`) —
внесены в SECURITY.md как осознанно принятый риск с условием снятия.
Проверка автоматизирована в CI.

**№4 Kirish darajasi (RBAC, 2FA, Session log, OTP)** 🔴 — **главное расхождение**

| Заявлено | Как было на деле | Как стало |
|---|---|---|
| «RBAC: Admin, Moderator, Seller, User» | `enum Role` в схеме существовал, но **ни один маршрут его не проверял**. Доступ держался на пароле в `sessionStorage`; из ~70 API-маршрутов авторизация стояла у 20 | Единый шлюз в `middleware.ts`: роль проверяется до обработчика, новый маршрут под защищённым префиксом закрыт по умолчанию |
| «4 xonali PIN» | Без счётчика попыток: 10 000 комбинаций перебирались меньше чем за 20 минут; успех не выдавал токена — клиент сам себе разрешал операции | Лимит 5 попыток/15 мин, успех выдаёт подписанную сессию с ролью SELLER |
| «Barcha kirish va amallar log fayllariga yoziladi» | Журнала не существовало. Кто изменил цену или удалил товар — установить было нельзя | `lib/audit.ts` → `logs/audit-<дата>.jsonl` + stdout: входы, отказы, смена пароля, обращения к персональным данным |
| 2FA / OTP | Нет | Нет. **Не заявлять** — вход по паролю + PIN, второй фактор не реализован |

Отдельно: пароль владельца был **захардкожен** в коде (`Microgreen2026`) и
действовал при отсутствии файла настройки — при том что репозиторий был
публичным. Заменён на scrypt с солью, при отсутствии настройки вход
закрывается (fail closed).

**№3 Foydalanuvchi ma'lumotlari (GDPR, PII)** 🟡
Было только про шифрование канала и локальное хранение. Механизма, которым
пользователь может забрать или удалить свои данные, не существовало.
**Дополнить:** «`POST /api/users/data` — выгрузка всех данных и удаление
(обезличивание). Личность подтверждается подписанным Telegram `initData`.
Заказы сохраняются обезличенными как первичный учётный документ.
Реализует ст. 20 Закона РУз «О персональных данных»».
