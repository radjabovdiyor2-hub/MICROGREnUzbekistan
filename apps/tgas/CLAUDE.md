# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

«Microgreen Uzbekistan» — набор независимых Telegram-ботов (aiogram 3), каждый из которых играет роль
AI-сотрудника (Sales, Support, Marketing, HR, Finance, PM, Analytics, Content, Stepan/помощник CEO,
DevOps, QA, R&D, n8n_bridge) для бизнеса по продаже микрозелени/гидропоники. Боты используют одну общую
CRM-базу Postgres и координируются через самописные event bus + task bus, а не через готовый фреймворк.
FastAPI-дашборд (`web_office/`) даёт read-view над той же БД. Есть также инстанс n8n
(`docker-compose.n8n.yml`) для workflow, которые не вписываются в Telegram/Python-часть (почта,
календарь) — до него достаёт `n8n_bridge`.

Весь код (докстринги, логи, промпты) на русском — придерживайтесь этого стиля при правках существующих
модулей.

## Запуск

Тестового набора, линтера или CI в проекте нет — `pytest`/`black`/`ruff` есть в `requirements.txt`, но не
используются. Файлы `test_*.py` в корне — это ручные скрипты (шлют реальные сообщения в Telegram / дёргают
реальные API токенами из `.env`), а не автоматизированный набор тестов. «Прогнать тесты» тут нечем —
проверяйте изменения, запуская нужного бота/скрипт напрямую против dev-`.env`.

**Но проверки есть, и они ловят ровно те поломки, которые не видны при чтении кода.
Прогоняйте всё это перед тем, как сказать «готово»** (инфраструктура не нужна):

```
python -m ruff check --select F .    # мёртвые и неопределённые имена
python -m pytest tests/ -q           # 286 тестов: инструменты, исполнитель, задачи, производство, цепь продажи, зеркало, распознавание намерения, шум оповещений, дедуп клиента, память разговора
python scripts/check_schema.py       # весь сырой SQL против schema.prisma
python scripts/check_tools.py        # инструменты, достижимость аргументов и подтверждений
python scripts/check_bot_roster.py   # состав 12 ботов + моста во всех шести местах
python scripts/check_prompts.py      # контакты и промпты
python scripts/check_imports.py      # `from shared.X import Y` — Y там есть
```

`check_imports.py` появился после 10.08.2026: `shared/feedback_loop.py`
импортировал `ai_engine`, которого в `shared/ai_engine.py` нет и не было, и
**весь слой самообучения не отработал ни разу** — падал на импорте у всех
одиннадцати ботов, а исключение почти везде глоталось. Тем же классом ошибки
оказалось сломано еженедельное обновление токена Instagram
(`auto_check_and_refresh_token` вместо `auto_refresh_token`). `ruff` такое не
ловит: он не разрешает импорты между модулями.

`tests/conftest.py` подменяет `mg_ai` заглушкой, если пакета нет (вне контейнера
он не ставится) — поэтому тесты идут и локально. Внутри Docker подмена не
срабатывает, и тесты идут против настоящего движка.

**Зелёный прогон сам по себе ничего не доказывает.** Правя любую из этих
проверок, убедитесь, что она умеет краснеть: подсуньте заведомую ошибку и
посмотрите, упадёт ли. Так нашлись две дыры — `check_schema` не разбирал
`алиас.колонка` (и пропустил `SUM(oi.subtotal)` по таблице без такой колонки),
а покрытие отделов в `check_tools` не могло упасть в принципе, потому что
общие инструменты есть у всех.

Отдельно, по потребности (ходят в сеть, нужны токены/ключи):

```
python scripts/check_bots_live.py    # getMe каждым токеном против bot_registry
python scripts/check_ai.py           # живая проверка AI-движка
```

Локальный venv лежит в `venv/` (Windows: `venv\Scripts\python.exe`).

**Инфраструктура (Postgres + Redis, нужна каждому боту):**
```

```

**Запуск одного бота локально** (каждый — самостоятельный процесс/entrypoint):

**Запуск веб-дашборда:**
```

```

**Запуск всего разом:** `start_all.ps1` / `start_all.bat` (Windows, поднимает каждого бота фоновым
процессом через локальный venv). Оба перечисляют ботов одним списком в начале файла — добавили бота,
допишите туда.

**⚠️ Реестр ботов дублируется в шести местах и умеет расходиться молча:** `shared/health.py`

прогоните сверку:

```
python scripts/check_bot_roster.py
```

Она ловит обе реальные ошибки, из-за которых мониторинг показывал 11/13: `analytics_bot`
импортировал `start_heartbeat` и не вызывал его (бот работал, но был невидим), а `franchise`
отсутствовал в прод-compose (на сервер его не разворачивали).

**Весь стек через Docker:**
```
docker compose up -d --build
```
Все контейнеры ботов собираются из одного корневого `Dockerfile` и различаются только `command:` (какой
модуль запускать). `devops` дополнительно монтирует Docker socket и `./backups` для бэкапов БД/операций с
контейнерами.

**Схема БД / сид-данные:**
- `database/init.sql` — схема, применяется автоматически при первом старте контейнера Postgres через
  `docker-entrypoint-initdb.d`. Для изменений схемы правьте этот файл — реальной миграционной тулзы нет
  (alembic есть в зависимостях, но не подключён).
- `database/seed_products.sql`, `scripts/seed_db.py` — засев каталога товаров.
- `scripts/build_knowledge_base.py` — сборка базы знаний support-бота.
- Разовые скрипты в корне (`migrate_v2.py`, `add_columns.py`, `fix_bots.py`, `patch_bots.py`,
  `recover.py`) — это исторические одноразовые скрипты миграций/патчей, а не повторяемый пайплайн: перед
  запуском читайте код, не полагайтесь на идемпотентность.

## Архитектура

### Структура одного бота
Каждый бот в `bots/<name>_bot/` устроен одинаково:
```
bots/<name>_bot/
├── main.py          # entrypoint: собирает Bot/Dispatcher, подключает роутеры, event bus, scheduler, слушатель bot-bus
├── states.py         # FSM-состояния aiogram
├── handlers/          # Router'ы aiogram (список all_routers экспортируется из handlers/__init__.py)
└── keyboards/          # билдеры inline-клавиатур
```
Более лёгкие сервисные боты (`devops_bot`, `qa_bot`, `rnd_bot`, `n8n_bridge`) — это однофайловый `main.py`
вообще без Telegram `Dispatcher`: это чистые воркеры event-bus/bot-bus или простые aiohttp
webhook-приёмники.

### Общая библиотека (`shared/`)
- `config.py` — единственный `Settings` (pydantic-settings), грузится из `.env`; используйте
  модуль-синглтон `settings`, не создавайте `Settings()` заново.
- `database.py` — асинхронный движок/сессии SQLAlchemy 2.0 (asyncpg). Бизнес-логика почти всегда работает
  через сырые запросы `sqlalchemy.text()` через `get_session_ctx()`, а не через ORM-модели — `Base`/
  `init_db()` существуют, но схемой владеет Prisma (`packages/database/prisma/schema.prisma`).
- **`tools/` — инструменты отделов (70 штук, 17 рискованных).** То, чем бот ДЕЛАЕТ работу,
  а не рассказывает о ней.
  `tools/registry.py` — дата-класс `Tool` и функции `tools_for(department)` / `schemas_for(...)` /
  `catalog_text(...)` (для планировщика совещаний) / `normalize_result(...)`;
  по файлу на отдел (`sales.py`, `finance.py`, `content.py`, `operations.py`, …), плюс
  `common.py` — общие для всех (`get_price_list`, `find_product`, `get_orders`, `get_tasks`,
  `create_task`, `delegate_to_department`, `human_task`, `get_business_summary`).
  Стёпан (`pm`, а также `production`/`logistics`/`operations`) видит все.
  **Тела инструментов ничего не реализуют** — зовут `sales_ops`, `catalog_ops`, `catalog_repo`,
  `storefront_orders`, `production_repo`, `capabilities`, `bot_bus`. Новая возможность →
  сначала ищите её там. Сверка: `python scripts/check_tools.py`.

  **Рискованный инструмент обязан быть достижим.** `risky=True` уходит в
  `shared/approvals.py`, а карточку надо чем-то отправить. У qa/rnd/devops нет
  Telegram-интерфейса — они зовут `execute_bot_task(bot=None)`, и заявка просто не
  создавалась: модель получала «подтвердить не удалось», а `run_backup`, единственное
  реальное действие DevOps, не выполнялся из задач НИ РАЗУ. Теперь у `approvals` есть
  запасной канал через бота Стёпана (`_fallback_bot`), и это проверяет
  `check_risky_tools_are_reachable` в `scripts/check_tools.py`.

  **Журнал пишется в свою таблицу, а не в `tasks`.** `log_quality_check` и `log_experiment`
  раньше вставляли строку в `tasks` со статусом `done` — при том, что `quality_controls`
  и `experiments` есть в схеме и их ведёт веб-админка. Ни отчёт `get_quality_report`,
  ни владелец на вкладке «ОТК» этих записей не видели никогда. Не заводите «журнал»
  задачей: сначала проверьте `schema.prisma`.

  **Один владелец на имя.** У Стёпана инструменты из двух источников: витрина
  (`apps/web/src/lib/stepan/*.ts` — цена товара, настройки, расписания ботов, обучение)
  и офис (`shared/tools/` — продажа, прайс, задачи, отчёты, CRM). `stepan_tools.load_registry`
  склеивает их с приоритетом офиса, а `is_native(name)` отвечает по реестру, а не по
  руками поддерживаемому списку. Раньше 12 имён из 24 существовали дважды и отвечали
  по-разному — например `get_content_status` брал данные из разных мест.
- `tool_runtime.py` — цикл «модель просит инструмент → выполняем → отдаём результат обратно».
  Обмен ведётся обычными `user`/`assistant`-сообщениями, а не ролью `tool`: движок один на два
  провайдера, и Gemini-ветка читает у сообщения только `content`.
- `approvals.py` — **единственный механизм подтверждения в Telegram**. Инструменты с
  `risky=True` (деньги, цены, каталог, сообщения клиентам) не выполняются сразу: владельцу
  уходит карточка с ✅/❌.
  Роутер `approvals_router` подключён в `main()` каждого Telegram-бота — без него кнопка
  не работает. Свой тип действия добавляется через `register_handler(kind, fn)`: так живут
  подтверждение изменяющих действий витрины (`storefront_write`) и запуск плана совещания
  (`meeting_plan`). Раньше это были три независимых механизма, два из которых держали
  заявки в словаре процесса и теряли их при рестарте.

  **Заявка не истекает.** Хранилище — таблица `owner_approvals`, а не Redis с TTL 15 минут.
  Прежний срок жизни означал ровно одно: не нажал за четверть часа — намерение исчезло, и
  никто об этом не узнал. Задача при этом навсегда оставалась в `todo`. Теперь заявка ждёт
  решения, `list_pending()` показывает очередь, а `remind_pending_approvals` у Стёпана
  напоминает с нарастающим интервалом (1 ч → 4 → 12 → 24). Решение атомарно
  (`UPDATE ... WHERE status='pending'`), поэтому двойное нажатие не выполнит действие дважды.

  **Порог самостоятельности — `Tool.auto_when`.** `risky=True` означало «спрашивать всегда»,
  и под это правило попало ВСЁ, что делает настоящую работу: списать два килограмма субстрата
  стоило владельцу столько же внимания, сколько рассылка по всей базе. Предикат получает
  аргументы вызова и пороги из настроек (`autonomy.*`, правятся в админке): уложился —
  выполняем сразу и докладываем постфактум строкой «🤖 Выполнено самостоятельно», не уложился —
  прежний путь через карточку. Порог 0 или недоступные настройки = спрашивать всегда.

  **У клиентских и публикующих действий порога быть не должно** (`register_sale`,
  `notify_customers`, `push_stale_orders`, `broadcast`, `b2b_offer`, `publish_content`,
  `publish_story`, `add_product`, `update_order_status`): отправленное письмо и вышедший
  пост не отзываются. Это закреплено тестом `test_customer_facing_tools_never_run_alone`.
- `alert_once.py` — **оповещения с памятью: пишем при изменении, а не каждый прогон.**
  Проверки по расписанию повторяли одно и то же, пока держалось условие: CSAT каждые
  2 часа (12 сообщений в сутки), крупные расходы и статус доставки по 6, аномалия
  выручки 4, просроченные платежи 3. `should_send(key, отпечаток)` пропускает только
  новое или изменившееся плюс напоминание раз в сутки; `resolved(key)` обязателен,
  когда повод ушёл, — иначе вернувшаяся проблема будет принята за «ничего не
  изменилось». Образец взят с `bot_health_check`: он бегает каждые 5 минут, а пишет
  при смене состава упавших ботов.

  **Задачу на каждый элемент списка не заводить.** `auto_task_creation` создавала
  задачу «Пополнить <товар>» на КАЖДЫЙ товар с низким остатком, и каждая будила
  Стёпана через `TASK_CREATED`: при 34 позициях — 69 сообщений и 34 вызова модели за
  прогон. Задача при этом невыполнима, пополнить готовый товар нечем. Такие сигналы
  идут строкой в утреннюю сводку (`grow_morning`), а не списком поручений.
- `catalog_repo.py` — **единственная дверь к каталогу** (витринные `products`/`categories`).
- `storefront_orders.py` — **единственная дверь к заказам** (`POST /api/orders`, смена статуса).
- `production_repo.py` — **единственная дверь к производству**: партии (`grow_batches`), приход
  сырья, смены, ОТК, опыты, маршруты. Тоже по HTTP в `/api/admin/*`, и по той же причине, что
  и заказы: посадка списывает сырьё по нормам культуры и складывает себестоимость партии,
  приход пересчитывает средневзвешенную цену, сбор урожая приходует товар с себестоимостью
  единицы. Эта арифметика живёт в `apps/web/src/lib/production/`, и вторая копия на Python
  разойдётся с первой. Своим SQL в офисе списывается только сырьё
  (`write_off_inventory` — вычитание с проверкой остатка в одном UPDATE).
  **Отказ витрины = отказ операции**, а не тихий успех: иначе «посадил» без партии.
- `ai_engine.py` — **обёртка, а не движок**. Сам транспорт (OpenAI primary + Gemini fallback, таблица
  стоимости токенов `TOKEN_COSTS`, эмбеддинги `embed()`, TTS/STT) живёт в `packages/mg_ai` и общий с
  витринным ботом. Здесь остаётся то, что специфично для офиса: ключи из `shared.config`, большой
  русско-узбекский системный промпт продаж (`MICROGREEN_SYSTEM_PROMPT`, это **f-строка** — телефон
  подставляется из настроек) и крючок `persist_fn`, который пишет расход в таблицу `ai_usage`.
  Пакет `mg_ai` ставится только внутри контейнера (`Dockerfile`: `pip install /opt/mg_ai`), поэтому
  вне Docker импорт движка упадёт — `shared/__init__.py` отдаёт `AIEngine` лениво, чтобы это не ломало
  статические сверки вроде `scripts/check_bot_roster.py`.

  **⚠️ Поставщик ОДИН — OpenAI. Запасного нет намеренно.** Раньше здесь была схема «OpenAI
  primary + Gemini fallback», и она молчала: пустой или неверный `OPENAI_API_KEY` не выключал ИИ,
  а переводил все 12 ботов на `gemini-2.5-flash` одной строкой `logger.warning`. Ветка Gemini для
  function calling слабее — нет `tool_choice`, история разворачивается в плоский текст, результаты
  инструментов идут обычными `user`-сообщениями. Именно так офис месяцами «тупил», и объяснением
  служило что угодно, кроме настоящей причины. **Тихая подмена хуже отказа: отказ видно сразу.**
  Теперь `chat_with_tools` при сбое поднимает исключение (вызывающий обязан назвать причину:
  у Стёпана это `_ai_error_reason`), `chat_completion` отдаёт честную заглушку, и в обоих случаях
  владельцу уходит сигнал (`on_failure` → `owner_alerts`, не чаще раза в сутки на причину).

  **Модель — одно значение `OPENAI_MODEL`**; пусто = дефолт из `shared/config.py`, сейчас `gpt-5.5`
  ($5/$30 за 1M) — самая умная из доступных по обычному ключу. Семейство `gpt-5.6-*` есть в прайсе,
  но раздаётся закрытым превью для партнёров с личным менеджером OpenAI: поставить его без доступа
  значит получить 400 на каждом вызове. Раньше конфиг,
  compose и `.env.example` называли три разные модели, и одна из них аккаунту не принадлежала —
  каждый вызов падал и уходил в Gemini.

  ⚠️ Две вещи ломаются молча при смене модели: `_is_reasoning_model` (рассуждающим нужен
  `max_completion_tokens`, а `max_tokens` они отвергают с 400) и `TOKEN_COSTS` (модели нет в
  словаре → расход в админке считается по ставке наугад). Обе проверяет
  `python scripts/check_ai.py` — он же делает живой вызов с инструментом и называет, какая модель
  реально ответила. Сверка была зелёной при полностью отсутствующем ключе.

  **⚠️ Инструменты ходят в /v1/responses, обычный текст — в /v1/chat/completions.** Это не
  вкусовщина: у `gpt-5.5` набор `tools` вместе с `reasoning_effort` на chat/completions
  отклоняется с 400 («use /v1/responses or set reasoning_effort to 'none'»). Второе означало бы
  выключить размышление ровно у того вызова, который решает, ЧТО сделать, поэтому переехал
  эндпоинт, а не уровень усилия. Следствия, о которые легко споткнуться: параметры зовутся иначе
  (`max_output_tokens` и `reasoning={"effort": ...}` вместо `max_completion_tokens` и
  `reasoning_effort`), схема инструмента у responses **плоская** (конвертирует
  `_to_responses_tools` в `mg_ai/engine.py`, схемы отделов остаются в chat-формате), а `store` там

### B2B лид-пайплайн (сбор ресторанов → рассылка → воронка)
Ежедневный цикл, завязанный на несколько отделов:
1. **03:00** `collect_leads_nightly` (marketing) → `shared.lead_gen` собирает рестораны из 2ГИС →
   `customers` со `status='lead'`, `customer_type='b2b'`, полями `source`/`source_ref`/`review_score`/
   `review_summary`. Дедуп по `(source, source_ref)` → телефону → названию.
2. **10:00** `b2b_outreach` (marketing) берёт **ровно `B2B_DAILY_LIMIT` (15)** свежих лидов (лучший рейтинг
   первым) и **ГОТОВИТ** им КП — но НЕ отправляет. Каждое уходит владельцу карточкой с ✅/❌, и письмо
   ресторану идёт только после нажатия. Здесь было написано «рассылает мультиканально»: по этому абзацу
   выходило, что холодные касания происходят сами, а на деле пайплайн целиком упирается в одного человека.
   Подготовленное помечается `interaction_type='b2b_offer_pending'`, отправленное — `'b2b_offer_sent'`;
   **оба** исключаются из завтрашней выборки. Пока исключался только `sent`, неподтверждённые карточки
   отбирались заново каждое утро: те же 15 ресторанов, новая генерация за деньги, дубли в `interactions`,
   и одно нажатие переводило в `sent` сразу всю накопленную пачку.
3. Ответы → Sales (квалификация → заказ), метрики → Analytics, стоимость → Finance, обзвон → PM/Sales.

⚠️ **Telegram-бот не может писать первым** (ограничение API) — холодный контакт идёт только через
email / телефон / IG DM, не через Telegram-рассылку.

### Модель межботового взаимодействия (важно при добавлении новой возможности боту)
Есть два независимых канала, и обычно нужны оба:
1. **Event bus** для «что-то произошло, кому надо — отреагирует» (broadcast, fire-and-forget, ответ не
   ожидается) — например, `ORDER_CREATED` от sales, который слушают Finance/PM/Analytics.
2. **Bot bus** для «сделай вот это конкретное и скажи результат» (целевой вызов, ждём результат) —
   например, Stepan делегирует `get_balance` в Finance и блокируется на `get_result()`.
Боту, который должен участвовать в делегированных задачах, нужны оба: обработчик `event_bus.on(...)` на
`TASK_CREATED` (чтобы реагировать на задачи, назначенные через диспетчер Stepan) *и* словарь
обработчиков действий bot_bus, переданный в `start_listener()` (чтобы работали прямые запрос/ответ).
Смотрите `finance_bot/main.py` как эталонный пример — там подключены оба канала плюс scheduler и роутер
групповых упоминаний.

**Как отдел выполняет задачу.** `handle_task_created` фильтрует по своему отделу и передаёт задачу
в `shared/task_executor.py` → `tool_runtime.run_tool_loop` с набором инструментов отдела. Отдел либо
ВЫПОЛНЯЕТ задачу инструментом, либо вызывает `delegate_to_department` — и тогда исполнитель меняется,
а событие `TASK_CREATED` уходит заново, плоским payload'ом и со счётчиком `hops` (после двух передач
задача уходит Стёпану, чтобы отделы не гоняли её по кругу). Своего разбора JSON у ботов больше нет.

**Маршрутизация задач по `department`.** Значения sales/support/finance/hr/marketing/analytics/
content/qa/rnd/devops обслуживают одноимённые боты — список продублирован в
`shared/tools/common.py::LISTENED_DEPARTMENTS`, и `scripts/check_tools.py` сверяет его с реестром
ботов. Отделы **pm / operations / production / logistics** своего бота НЕ имеют — их принимает
**Stepan** (он же PM/COO), туда же уходит всё нераспознанное. Добавляете новое значение
`department` — добавьте его в `LISTENED_DEPARTMENTS`, иначе задача создастся в БД, событие
улетит, а исполнителя не будет (был такой баг с `operations`).

Здесь же значилось «и в `CLASSIFIER_PROMPT` диспетчера». Такой константы больше нет: AI-классификатор
из `stepan_bot/handlers/dispatcher.py` убран, отдел определяет модель через инструменты, а сам промпт
лежал мёртвым грузом. Правка по этой инструкции уходила в никуда.

Фильтр писать **строго так**, с приведением регистра и значением по умолчанию:

```python
if str(data.get("department", "")).lower() != "qa":
    return
```

`devops_bot`, `qa_bot` и `rnd_bot` раньше сравнивали `data.get("department") != "qa"` без
`.lower()`, и задача с `department="QA"` от диспетчера молча терялась.

**`franchise` задач не принимает — и это намеренно.** `franchise_bot` — планировщик: раз в день
собирает сводку для франчайзи по городам, на события event bus не подписан и обработчика
`TASK_CREATED` не имеет. Не ищите его — диспетчер такой `department` и не выдаёт. Если франшизе
понадобятся делегированные задачи, добавлять придётся оба канала сразу (`event_bus.on` +
`start_listener`), иначе повторится история с `operations`.

**bot_bus: у кого есть слушатель.** `start_listener` подключён у всех, кроме `franchise_bot`
(он планировщик и задач не принимает — см. выше). Первым аргументом `send_task` везде передаётся
`"stepan_bot"` (не `"stepan"`): значение идёт только в лог и в поле задачи, но пусть будет
одинаковым, иначе логи шины не читаются.

### База данных
База одна, но таблицы в ней **двух семейств**, и это главное, что надо знать перед любым SQL.

| Кому принадлежит | Таблицы | Ключи |
|---|---|---|
| Витрина (Prisma) | `products`, `categories`, `orders`, `order_items`, `users`, `employees` | cuid-строки |
| CRM офиса | `crm_products`, `crm_orders`, `crm_order_items`, `crm_employees`, `customers`, `interactions`, `tasks`, `finances`, `followups`, `inventory`, `ai_usage` | `serial` |

`unify_databases.sql` переименовал офисные `products/orders/order_items/employees` в `crm_*`,
отдав короткие имена витрине. **Схемой владеет Prisma** (`packages/database/prisma/schema.prisma`);
`database/init.sql` — исторический файл, он описывает состояние ДО переименования и больше никуда
не монтируется.

**Что из этого следует:**
- Каталог читать **только** через `shared/catalog_repo.py` — там витринные колонки. Своего SQL к
  товарам не писать.
- Заказ создавать **только** через `shared/storefront_orders.py` (`POST /api/orders`). Заказами
  владеет витрина: она выдаёт номер, списывает остаток, уведомляет клиента и зеркалит заказ в
  `crm_orders` через `/ingest/order`, откуда уходит `ORDER_CREATED`.
- Отчёты офиса считать по `crm_orders`/`crm_order_items`: через зеркало проходит каждый заказ —
  и с сайта, и зарегистрированный менеджером.

**⚠️ Проверяйте колонки скриптом, а не догадками:** `python scripts/check_schema.py`. Он сверяет
весь сырой SQL со `schema.prisma`. Раньше он сверял с `init.sql` и именно поэтому пропустил
самую дорогую поломку проекта: `SELECT ... unit FROM products` проходил проверку, хотя в живой
базе `products` — таблица витрины и `unit` там нет. Регистрация продажи молча отвечала «не смог
записать продажу в БД», прайс-лист приходил пустым, и модель дописывала цены сама.

**⚠️ Новую таблицу создаёт Prisma.** `CREATE TABLE IF NOT EXISTS` в рантайме — крайняя мера
(так живут `meeting_state`, `ig_comment_seen`, `franchise_journals`). Правьте `schema.prisma`
и делайте `npm run db:push`.

**Сравнение строк регистрозависимое.** `tier = 'premium'` не находил записи с `PREMIUM`, и
рубрика «Ресторан недели» не выходила ни разу; города пишут и латиницей, и кириллицей.
Сравнивайте через `LOWER(...)`, для городов — со списком написаний (`CITY_SPELLINGS` в
franchise_bot). Та же болезнь, что с `department` без `.lower()`.

**База на проде одна.** Все сервисы в `docker-compose.prod.yml` смотрят в `microgreen` —
и витрина, и боты, и `web_office`. Отдельного `STOREFRONT_DATABASE_URL` и функции
`get_storefront_session_ctx()` больше нет: витринные таблицы читаются обычной сессией
(см. таблицу владения выше).

**Дата операции против времени записи.** В `finances` есть `date` — деловая дата, её можно
проставить задним числом, — и `created_at` — момент внесения строки. **Отчёты считайте по
`date`**: месячный P&L считал по `created_at`, и расход, внесённый задним числом, исчезал из
отчёта, завышая прибыль. По `date` считают analytics, stepan и экран баланса самого finance.

Часовой пояс базы — `Asia/Samarkand`, задан **аргументом запуска** в обоих compose: на уже
созданном томе `timezone` берётся из `postgresql.conf` и переменные окружения его не перебивают.
До этого база жила в UTC, и операции с полуночи до 5 утра по местному получали вчерашнюю дату;
уже записанные значения не пересчитывались. Не смешивайте в одном сравнении
`created_at AT TIME ZONE ...` (колонка без пояса) и `NOW() AT TIME ZONE ...` (значение с поясом) —
они разворачивают время в разные стороны, и сравнение не сходится.

- Корень репозитория захламлён сгенерированными/рантайм-артефактами (`*.log`, `microgreen.db`,

  правки.
- `.env` содержит похожие на настоящие секреты (токены ботов, ключ OpenAI, токены Instagram/Facebook) —
  никогда не выводите его содержимое и не коммитьте изменения, которые его раскрывают.
- `1/` в корне репозитория не является значимым пакетом (странная оставшаяся директория) — проверяйте
  содержимое, прежде чем считать её релевантной задаче.
